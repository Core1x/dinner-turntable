# 附近餐厅随机转盘（Dinner Wheel）实现方案

## 一、项目目标

开发一个基于真实地理位置的附近餐厅随机选择网页应用。

核心功能：

1. 获取用户当前地理位置。
2. 调用高德地图 API 查询附近真实餐厅。
3. 根据距离、餐饮类别、人均消费进行筛选。
4. 将筛选后的餐厅动态生成转盘。
5. 用户点击按钮旋转转盘，随机决定今晚去哪家餐厅。
6. 展示抽中的餐厅信息，并支持跳转地图导航。

项目最终部署到 Cloudflare Pages，用户通过手机或电脑浏览器访问，无需安装客户端。

**核心原则：不使用虚构餐厅数据，不接入 AI，不建设自己的餐厅数据库。**

## 四、核心功能设计

### 4.1 首页

设计一个简洁、现代、适合移动端的单页应用。

页面主要区域：

1. 顶部：产品名称「今晚吃什么」。
2. 位置区域：显示当前定位或手动选择的地点。
3. 筛选区域：搜索半径、餐饮类别、人均预算。
4. 餐厅区域：展示查询到的餐厅数量和候选列表。
5. 转盘区域：展示动态生成的餐厅转盘。
6. 结果区域：展示最终抽中的餐厅。

视觉风格：
- 简洁、现代、轻量。
- 适当使用卡片、圆角和阴影。
- 转盘使用鲜明但协调的颜色。
- 优先适配手机屏幕，同时兼容桌面浏览器。
- 不要使用过于复杂的后台管理系统风格。

### 4.2 地理位置获取

使用浏览器 Geolocation API。

调用：

navigator.geolocation.getCurrentPosition()

要求：
- 用户主动点击「定位附近餐厅」后才申请定位权限。
- 获取经纬度和定位精度。
- 设置合理的定位超时时间。
- 定位失败时给出明确提示。
- 用户拒绝授权时，允许手动输入地址。
- 不要将用户的精确坐标持久化保存。

手动地址输入：
- 用户输入城市、街道或地标。
- 通过高德地理编码 API 转换为坐标。
- 支持重新搜索。

### 4.3 餐厅查询

使用高德地图 Web 服务 API。

主要接口：

GET https://restapi.amap.com/v5/place/around

主要参数：
- key：服务端 API Key。
- location：经度,纬度。
- radius：搜索半径。
- types：餐饮服务类别。
- page_size：每页数量。
- page_num：页码。
- show_fields：按官方文档请求所需商业字段。

餐饮类别以高德餐饮 POI 分类为基础。

第一版查询范围：
- 全部餐饮
- 中餐
- 快餐
- 面食
- 其他餐饮

优先查询全部餐饮 POI，再根据返回的类别编码进行筛选。

需要支持分页，避免只获取第一页数据。

建议每次最多获取 50 条候选数据，具体数量根据 API 配额和接口限制调整。

### 4.4 餐厅数据标准化

后端返回统一数据结构：

{
  "id": "高德POI_ID",
  "name": "餐厅名称",
  "address": "餐厅地址",
  "location": {
    "lng": 113.9,
    "lat": 22.6
  },
  "distance": 500,
  "category": "中餐",
  "rating": 4.5,
  "averagePrice": 35,
  "businessHours": null,
  "telephone": null
}

注意：
- 所有非必填字段允许为空。
- 不要自行生成评分、人均价格或营业时间。
- 缺失的数据显示「暂无数据」。
- 使用 POI ID 去重。
- 如果没有 POI ID，再使用名称和地址辅助去重。

### 4.5 筛选功能

搜索半径：
- 500 米
- 1 公里
- 2 公里
- 3 公里

人均预算：
- 25 元以内
- 40 元以内
- 60 元以内
- 不限

餐饮类别：
- 全部
- 中餐
- 快餐
- 面食
- 其他

筛选逻辑：
1. 根据用户选择的半径获取餐厅。
2. 根据类别进行筛选。
3. 根据人均价格进行筛选。
4. 价格缺失的餐厅标记为「价格未知」，不要伪造价格。
5. 筛选结果为空时给出提示，并允许扩大范围。

不要将缺少营业时间数据的餐厅错误标记为营业中。
第一版不强制实现实时营业状态判断。

### 4.6 动态转盘

这是整个产品的核心交互。

要求：
- 根据筛选后的真实餐厅动态生成扇区。
- 每个扇区对应一家餐厅。
- 默认最多展示 8 家，允许调整候选数量。
- 餐厅数量不足 2 家时禁止旋转。
- 每个候选餐厅默认具有相同中奖概率。
- 转盘具有流畅的旋转动画。
- 使用固定指针指向最终结果。
- 旋转结束后显示中奖餐厅。

实现建议：
使用 SVG 或 CSS conic-gradient 实现扇区，使用 CSS transform 和 transition 实现旋转动画。

需要特别注意：
- 随机选择的餐厅必须与最终指针指向的扇区一致。
- 不能出现动画结束后显示的餐厅与实际指针位置不一致。
- 转盘需要适配不同数量的餐厅。
- 动画期间禁止重复点击。

### 4.7 抽取结果

抽中餐厅后展示：

- 餐厅名称
- 餐厅地址
- 距离
- 人均消费（有数据时）
- 评分（有数据时）
- 营业时间（有数据时）

提供三个操作：

1. 「就是这家」：确认选择。
2. 「再抽一次」：重新随机选择。
3. 「查看地图」：跳转高德地图查看餐厅位置或导航。

地图链接应使用高德官方 URI 格式，确保坐标系参数正确。

### 4.8 历史记录

第一版可以使用 localStorage 保存：
- 最近抽中的餐厅。
- 抽取时间。
- 餐厅名称和地址。

支持查看最近的抽取记录。

不需要用户注册和云端同步。

## 五、后端 API 设计

使用 Cloudflare Pages Functions。

### GET /api/restaurants

查询附近餐厅。

参数：
- lng
- lat
- radius
- category
- page

职责：
1. 校验参数。
2. GPS 坐标转换。
3. 调用高德周边搜索。
4. 处理 API 异常。
5. 标准化返回数据。

### GET /api/geocode

根据用户输入的地址获取坐标。

参数：
- address
- city（可选）

调用高德地理编码接口。

返回：
- 标准化地址
- 经度
- 纬度

### 后端安全要求

高德 Web 服务 API Key 必须保存在 Cloudflare Secrets 中。

环境变量名称：

AMAP_WEB_KEY

禁止：
- 将 API Key 写入 Vue 前端。
- 使用 VITE_ 前缀暴露服务端密钥。
- 将密钥提交到 GitHub。
- 在日志中打印用户精确坐标。
- 将上游完整错误信息和密钥返回给前端。

本地开发使用 `.dev.vars`，并加入 `.gitignore`。

对半径、分页、经纬度和地址长度进行参数限制。前端增加请求冷却，后续可以增加 Cloudflare 限流规则和缓存。

验收：所有主要流程可正常使用，异常情况有明确提示。

### Phase 6：Cloudflare 部署

1. 在 GitHub 创建项目仓库。
2. 提交项目代码。
3. 在 Cloudflare 创建 Pages 项目。
4. 关联 GitHub 仓库。
5. 配置构建命令：npm run build。
6. 配置输出目录：dist。
7. 配置 Secret：AMAP_WEB_KEY。
8. 发布项目。
9. 验证线上页面和 API。

本地 Pages Functions 调试使用 Wrangler，确保本地 `.dev.vars` 配置有效。

最终生成可公开访问的 HTTPS 地址。

## 八、项目验收标准

第一版完成时必须满足：

- 能获取用户真实地理位置。
- 能查询附近真实存在的餐厅。
- 能按照距离、类别和预算筛选。
- 能根据查询结果动态生成转盘。
- 能正确随机抽取餐厅。
- 抽取结果与转盘指针保持一致。
- 能查看餐厅地址和可用的商业信息。
- 能跳转地图。
- 能在手机浏览器正常使用。
- 能部署到 Cloudflare Pages。
- 不需要本地服务器持续运行。
- API Key 不暴露在前端。
- 不依赖虚构数据。
